# 룰 매칭 및 UI·백엔드 연동 개발 보고서

## 1. 담당 파트 개요

본 프로젝트는 외국인 계절근로자의 근로계약서, 근무기록부, 임금명세서, 입금내역서를 비교하여 계약·근무·급여 사이의 불일치를 확인하고 관련 법령과 대응 방법을 안내하는 서비스이다.

담당한 부분은 크게 두 가지이다.

1. OCR로 구조화된 문서 데이터를 입력받아 R00~R11 규칙으로 비교·판정하는 룰 매칭 엔진 구현
2. 사용자가 문서를 올리고 OCR 결과를 확인한 뒤 급여 거래를 선택하고 최종 결과를 확인할 수 있도록 UI를 제작하고 백엔드 API와 연결

룰 엔진은 법 위반을 직접 확정하는 모델이 아니라 문서 간 값의 불일치, 계산상 차이, 추가 확인이 필요한 상태를 구분하는 역할을 한다. LLM은 이 판정을 다시 계산하지 않고 이미 확정된 판정과 공식 근거를 사용자가 이해하기 쉽게 설명하는 역할만 담당한다.

## 2. 개발 목표

- 최종 표준피처정의서와 JSON Schema v6를 기준으로 일관된 입력·출력 구조를 사용한다.
- 근로자가 직접 확인하기 어려운 계약, 근무시간, 수당, 공제, 입금액 차이를 자동으로 비교한다.
- 자료가 부족한 경우 임의로 정상 또는 오류 처리하지 않고 `NOT_CHECKABLE`로 구분한다.
- OCR 오류 가능성을 고려하여 사용자가 추출값을 직접 확인하고 수정한 뒤 규칙을 실행한다.
- 내부 필드명과 계산용 JSON을 그대로 노출하지 않고 쉬운 한국어 항목명과 판정 근거를 제공한다.
- 공휴일 및 법령처럼 외부 기준이 필요한 항목은 공식 API와 공식 자료를 사용한다.
- API 장애가 발생해도 규칙 판정 자체는 유지되고 고정 안내 문구를 제공하도록 한다.

## 3. 룰 매칭 개발 과정

### 3.1 입력 데이터 표준화

OCR 모듈이 생성하는 v6 `documents`를 룰 엔진의 입력으로 사용하였다. 문서 종류는 다음 네 가지이다.

- `contract`: 표준근로계약서
- `timesheet`: 근무기록부
- `payslip`: 임금명세서
- `bank_statement`: 입금내역서

날짜, 시간, 금액, 불리언 값의 표현 차이로 비교 오류가 발생하지 않도록 정규화 단계를 적용했다. 계산 결과는 `derived`, 규칙별 판정은 `rule_results`에 저장하여 v6 Schema 구조를 유지했다.

### 3.2 R00~R11 규칙 구현

| 규칙 | 검사 내용 | 주요 구현 내용 |
|---|---|---|
| R00 | 문서 연결 확인 | 문서별 근로자명, 사업장, 대상 기간의 일치 여부 확인 |
| R01 | 계약 임금 비교 | 동일 임금형태는 0원, 시간급 환산 비교는 ±10원 기준 적용 |
| R02 | 근무시간 비교 | 근무기록일수÷소정근로일수 커버리지 90% 이상인 경우에만 비교 |
| R03 | 상여금·수당 비교 | 계약상 약정 금액과 명세서 지급액 및 연장근로수당 비교 |
| R04 | 숙식비 공제 비교 | 계약상 근로자 부담액과 명세서 공제액 비교 |
| R05 | 공제 합계 검산 | 공제항목 합계와 총공제액 비교, 시간 비례 허용오차 적용 |
| R06 | 지급 합계 검산 | 지급항목 합계와 총지급액을 허용오차 0원으로 비교 |
| R07 | 실수령액 검산 | 총지급액−총공제액과 실수령액 비교, 시간 비례 허용오차 적용 |
| R08 | 실제 입금액 비교 | 사용자가 선택한 복수 급여 거래의 합계와 실수령액 비교 |
| R09 | 지급일 확인 | 계약상 지급일과 전액 지급 완료일 비교, 공휴일이면 직전 영업일만 정상 처리 |
| R10 | 근로시간 변경 확인 | 일별 상한 초과, 변경 사유, 근로자 확인 여부 검사 |
| R11 | 최저임금 위험 확인 | 적용연도의 최저임금과 계약·명세서 환산시급 비교 |

판정 상태는 `PASS`, `MISMATCH`, `REVIEW`, `REVIEW_HIGH`, `NOT_CHECKABLE`로 구분했다. 특히 값이 없거나 자료가 충분하지 않은 경우 0으로 자동 변환하지 않고 `NOT_CHECKABLE`로 처리하여 잘못된 확정 판정을 방지했다.

### 3.3 외부 API 연동

R09는 공공데이터포털 공휴일 API를 사용한다. 지급 예정일이 주말 또는 공휴일인 경우 계약 정책에 따라 직전 영업일을 계산한다. API 키는 코드에 저장하지 않고 `.env`에서 읽도록 구성했으며, API 조회에 실패하면 지급일을 임의로 판정하지 않고 사람이 확인하도록 한다.

### 3.4 법령 RAG·LLM 연결

규칙별 법령 근거는 고정 매핑을 우선 사용하고, 수집된 공식 법령 코퍼스에서 실제 조문을 조회한다. LLM 모델은 `gpt-4.1-mini`를 사용하며 쉬운 설명, 추가 확인사항, 추가 질문, 다음 행동을 생성한다.

비교값과 법령 근거는 결정적 데이터로 유지하여 LLM이 변경할 수 없도록 했다. LLM 출력의 숫자 변조와 금지 표현을 검사하고, API 키가 없거나 호출에 실패하면 규칙별 고정 문구로 전환한다.

## 4. UI 및 백엔드 연결 과정

### 4.1 사용자 흐름 설계

UI는 다음 다섯 단계로 구성했다.

1. 문서 4종 업로드
2. OCR 추출값 확인 및 수정
3. 실제 급여 입금 거래 선택
4. 분석 전 최종 확인
5. R00~R11 결과와 법령 안내 확인

사용자가 OCR 결과를 그대로 신뢰하지 않도록 확인 단계를 두었다. 조건상 필요하지 않은 빈 필드는 `확인 필요`가 아니라 `해당 없음`과 이유를 표시했다. 내부 필드명 대신 `근로자 이름`, `계약 임금`, `실수령액`과 같은 사용자용 명칭을 사용했다.

### 4.2 API 구성

Python 표준 HTTP 서버에 다음 API를 구성했다.

- `GET /api/health`: 서버, Schema, OCR 장치 및 모델 캐시 상태 확인
- `GET /api/demo`: 예시 문서 데이터 제공
- `POST /api/ocr`: PDF 4종을 받아 OCR 및 v6 documents 생성
- `POST /api/evaluate`: 사용자 확정 데이터를 받아 규칙 판정과 법령 설명 생성

프론트엔드는 `fetch`를 이용해 각 API를 호출한다. OCR 완료 후 반환된 canonical JSON을 화면 입력값과 연결하고, 사용자가 수정한 값과 선택한 거래를 다시 `/api/evaluate`로 전달한다.

### 4.3 다국어 UI

한국어와 캄보디아어(크메르어)를 선택할 수 있는 드롭다운을 상단에 추가했다. 언어를 변경해도 업로드한 파일과 현재 입력 상태가 유지되며, 선택 언어는 브라우저에 저장된다. 고정 문구뿐 아니라 OCR 필드, 거래 선택, 규칙 상태, 결과 요약 등 동적으로 생성되는 화면도 번역한다. 캄보디아어 선택 상태에서 규칙을 실행하면 LLM 사용자 안내 역시 캄보디아어로 생성한다.

## 5. 검증 결과

- Python 3.11 환경에서 규칙 엔진 단위 테스트 5개 통과
- JavaScript 문법 검사 통과
- 최종 v6 JSON Schema 검증 통과
- 공휴일 API 실제 조회 성공
- OpenAI API 구조화 출력 6개 필드 생성 성공
- LLM 설명 과정에서 기존 규칙 판정 변경 없음
- 합성 PDF 4종 업로드 후 OCR, 파싱, 문서 Schema 검증 성공
- 법령 설명 기존 검증에서 합성 JSON 180세트 리포트 생성 및 판정 불일치 0건 확인

## 6. 개발 효과

### 6.1 사용자 측면

- 여러 문서를 직접 대조해야 하는 부담을 줄일 수 있다.
- OCR 결과를 사용자가 수정할 수 있어 자동 인식 오류를 보완할 수 있다.
- 단순히 `불일치`만 표시하지 않고 어떤 값을 비교했는지와 다음 행동을 함께 확인할 수 있다.
- 전문적인 법령 내용을 쉬운 언어로 확인할 수 있다.
- 캄보디아어 UI를 통해 한국어가 익숙하지 않은 근로자의 접근성을 높일 수 있다.

### 6.2 시스템 측면

- 규칙 판정과 LLM 설명을 분리하여 생성형 AI가 계산 결과를 바꾸는 위험을 줄였다.
- v6 Schema를 사용하여 OCR, 룰 엔진, UI, 법령 설명 사이의 데이터 형식을 통일했다.
- 외부 API나 LLM이 실패해도 `NOT_CHECKABLE` 또는 고정 문구로 안전하게 동작한다.
- 규칙별 비교 근거를 구조화하여 향후 테스트와 오류 분석이 가능하다.

## 7. 한계

- CPU 환경에서 PaddleOCR로 문서 4종을 처리하면 수 분 이상 걸릴 수 있다.
- OCR 정확도는 문서 화질, 표 구조, 글꼴 및 스캔 상태에 영향을 받는다.
- 현재 OCR 전체 데이터에 대한 필드별 정량 성능평가는 아직 완료되지 않았다.
- 규칙은 제출된 네 문서의 정합성을 확인하는 도구이며 실제 법 위반을 확정하지 않는다.
- 사업장 업종, 별도 합의, 지역별 행정지침 등 입력에 없는 사실은 판단할 수 없다.
- LLM 설명은 공식 근거 안에서 생성하도록 제한했지만 최종적인 법률 자문을 대신할 수 없다.
- 캄보디아어 번역은 실제 캄보디아인 사용자를 대상으로 표현의 자연스러움과 이해도를 추가 검증해야 한다.

## 8. 향후 계획

1. 전체 합성 PDF를 이용한 OCR 필드별 정확도와 누락률 측정
2. OCR 수정 전·후 R00~R11 판정 정확도 비교
3. LLM의 숫자 보존, 근거 일치, 과도한 법적 단정 여부 평가
4. 캄보디아어 원어민 검수 및 사용자 테스트
5. OCR 모델 경량화, 결과 캐싱 및 GPU 적용 가능성 검토
6. 회의록에서 확인된 R03 비교값, 추가 확인사항 기본 문구 등 후속 UI 개선
7. 최종 발표용 시연 사례와 결과 화면 정리

## 9. 결론

룰 매칭 엔진과 UI·백엔드 연결을 통해 네 종류의 문서를 업로드하는 단계부터 OCR 확인, 급여 거래 선택, 규칙 판정, 법령 안내까지 하나의 사용자 흐름으로 통합했다. 본 구현은 AI가 임금 문제를 임의로 판단하는 방식이 아니라, 결정적 규칙으로 차이를 확인하고 AI가 그 결과를 쉽게 설명하는 구조라는 점에 의미가 있다. 향후 OCR 성능평가와 다국어 사용자 검증을 수행하면 실제 현장 적용 가능성을 보다 구체적으로 평가할 수 있다.
